# JetLend — промокоды при создании заказа

Тестовое Django-приложение с HTTP endpoint для создания заказа и применения
процентного промокода. Решение использует PostgreSQL, проверяет бизнес-правила
промокодов и защищает общий лимит использований от конкурентных запросов.

## Возможности

- создание заказа из нескольких товарных позиций;
- необязательный промокод;
- проверка срока действия и общего лимита промокода;
- запрет повторного использования одним пользователем;
- ограничение промокода одной разрешённой категорией;
- исключение отдельных товаров из любых акций;
- расчёт скидки отдельно для каждой позиции;
- сохранение исторических snapshot-цен и названий товаров;
- атомарное создание заказа и учёт использования промокода;
- единый формат API-ошибок;
- OpenAPI-схема со Swagger UI и ReDoc;
- структурированное логирование создания и отклонения заказов;
- Django admin и команда наполнения demo-данными.

## Технологии

- Python 3.12+;
- Django 5.2;
- Django REST Framework;
- drf-spectacular для OpenAPI-документации;
- PostgreSQL 16;
- `uv` для зависимостей и виртуального окружения;
- Gunicorn для production-запуска;
- Ruff, mypy и django-stubs;
- Docker и Docker Compose.

## Архитектура

| Компонент | Ответственность |
|---|---|
| `catalog` | Категории и товары |
| `promocodes` | Промокоды и журнал использований |
| `orders` | Заказы, расчёт скидки, сервис создания и API |
| `config/api` | Единый формат HTTP-ошибок |
| `common` | Переиспользуемые инфраструктурные компоненты |

HTTP-слой не содержит бизнес-логики:

```text
POST /api/orders/
  → CreateOrderInputSerializer
  → CreateOrderService
  → DiscountCalculator
  → PostgreSQL transaction
  → OrderOutputSerializer
```

Подробный анализ и принятые решения находятся в
[`docs/implementation-plan.md`](docs/implementation-plan.md).

## Бизнес-правила промокода

Промокод применяется, только если:

1. код существует и активен;
2. срок действия не истёк;
3. общий лимит `max_uses` не исчерпан;
4. пользователь раньше не применял этот код;
5. товар входит в `allowed_category`, если она задана;
6. товар не помечен как `is_discount_excluded`.

`allowed_category=NULL` означает, что категория не ограничена. В заказе могут
быть товары разных категорий: скидку получат только подходящие позиции.

Все деньги хранятся целым количеством копеек в полях с суффиксом `_minor`.
Процентная скидка рассчитывается и округляется до копейки отдельно для каждой
позиции. `float` в бизнес-расчётах не используется.

## Локальный запуск

Необходимы установленные `uv`, Docker и Docker Compose.

```bash
cp .env.example .env
make install
make db-up
make migrate
make seed-demo
make run-dev
```

Приложение будет доступно на <http://127.0.0.1:8000/>, административная панель
— на <http://127.0.0.1:8000/admin/>.

Создание администратора:

```bash
make superuser
```

## Быстрая проверка API

Команда ниже идемпотентно создаёт demo-пользователя, две категории, три товара
и промокод `SUMMER2025`:

```bash
make seed-demo
```

Она выводит готовое тело запроса с актуальными ID. Пример:

```bash
curl -X POST http://127.0.0.1:8000/api/orders/ \
  -H "Content-Type: application/json" \
  -d '{
    "user_id": 1,
    "goods": [
      {"good_id": 1, "quantity": 2},
      {"good_id": 2, "quantity": 1},
      {"good_id": 3, "quantity": 1}
    ],
    "promo_code": "SUMMER2025"
  }'
```

Demo-набор содержит:

- книгу за 100 рублей из разрешённой категории;
- игру за 50 рублей из другой категории;
- подарочную карту за 25 рублей, исключённую из акций.

При количестве книги `2` ожидаемая стоимость заказа — 275 рублей, скидка —
20 рублей, итог — 255 рублей.

## API

### Интерактивная документация

| Адрес | Назначение |
|---|---|
| `/api/docs/` | Swagger UI, из него можно отправить запрос |
| `/api/redoc/` | ReDoc |
| `/api/schema/` | OpenAPI 3 схема в YAML, `?format=json` для JSON |

Схема генерируется из serializers и аннотаций view через drf-spectacular.
Сохранить её в файл можно командой `make schema`, которая заодно проверяет
схему на предупреждения генератора.

### Создание заказа

```http
POST /api/orders/
Content-Type: application/json
```

Тело запроса:

```json
{
  "user_id": 1,
  "goods": [
    {
      "good_id": 1,
      "quantity": 2
    }
  ],
  "promo_code": "SUMMER2025"
}
```

`promo_code` можно не передавать. Цены и скидки клиент не передаёт: сервис
всегда получает их из PostgreSQL.

Успешный ответ, `201 Created`:

```json
{
  "user_id": 1,
  "order_id": 1,
  "goods": [
    {
      "good_id": 1,
      "quantity": 2,
      "price": 100,
      "discount": "0.1",
      "total": 180
    }
  ],
  "price": 200,
  "discount": "0.1",
  "total": 180
}
```

`discount` — строковый коэффициент: `"0.1"` означает 10%, `"0"` — отсутствие
скидки. `price` позиции — цена одной единицы товара, а `total` позиции уже
учитывает количество и скидку.

### Ошибки валидации

```json
{
  "code": "invalid_request",
  "detail": "Ошибка валидации запроса.",
  "errors": {
    "goods": {
      "non_field_errors": [
        {
          "message": "Заказ должен содержать хотя бы один товар.",
          "code": "empty"
        }
      ]
    }
  }
}
```

### Доменные ошибки

```json
{
  "code": "promo_code_expired",
  "detail": "Срок действия промокода истёк."
}
```

Возможные коды:

| Код | Причина |
|---|---|
| `invalid_request` | Некорректная структура или состав заказа |
| `user_not_found` | Пользователь не существует |
| `good_unavailable` | Товар отсутствует или неактивен |
| `promo_code_not_found` | Промокод отсутствует или отключён |
| `promo_code_expired` | Срок действия истёк |
| `promo_code_usage_limit_reached` | Общий лимит исчерпан |
| `promo_code_already_used` | Пользователь уже использовал промокод |
| `promo_code_not_applicable` | В заказе нет подходящих товаров |

## Целостность и конкурентные запросы

`CreateOrderService` выполняется внутри `transaction.atomic()`:

1. товары блокируются через `select_for_update()`;
2. промокод также блокируется до проверки лимита;
3. создаются заказ и snapshot-позиции;
4. создаётся уникальная запись `PromoCodeUsage`;
5. `used_count` атомарно увеличивается через `F()`;
6. при любой ошибке вся операция откатывается.

Уникальное ограничение `(promo_code, user)` запрещает повторное использование
на уровне БД. Конкурентный интеграционный тест подтверждает, что два запроса не
могут одновременно забрать последнее доступное применение.

## Логирование

Все логи пишутся в stdout в формате `время уровень [logger] сообщение`, чтобы
их собирал Docker, systemd или любой агрегатор. Уровень задаётся переменной
`DJANGO_LOG_LEVEL` (по умолчанию `INFO`), SQL-запросы включаются отдельно
через `DJANGO_DB_LOG_LEVEL=DEBUG`.

Что попадает в логи:

| Событие | Logger | Уровень |
|---|---|---|
| Заказ создан: id заказа, пользователь, промокод, суммы в копейках | `orders.services.create_order` | INFO |
| Заказ отклонён бизнес-правилом: код и причина | `config.api.exception_handler` | INFO |
| Ошибка валидации запроса: список полей | `config.api.exception_handler` | INFO |
| Прочие ошибки API: 404, 405, 415 и т. п. | `config.api.exception_handler` | WARNING |
| Необработанные исключения с traceback | `django.request` | ERROR |

Тело запроса и персональные данные в логи не попадают, только идентификаторы.

## Docker

### Development

Dev-стек запускает Django `runserver` с autoreload и монтирует исходный код:

```bash
make docker-dev
```

Остановка:

```bash
make docker-dev-down
```

### Production-like

```bash
cp .env.example .env
# Замените значения на реальные production-значения, см. таблицу ниже.
make docker-up
```

Сервис `app` ждёт готовности PostgreSQL, применяет миграции и запускает
Gunicorn. `docker-compose.yml` читает переменные из `.env`, значений по
умолчанию у production-конфигурации нет:

| Переменная | Назначение |
|---|---|
| `DJANGO_SECRET_KEY` | Длинный случайный секрет |
| `DJANGO_ALLOWED_HOSTS` | Домены через запятую, например `example.com` |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Origins через запятую, например `https://example.com` |
| `DJANGO_LOG_LEVEL` | Уровень логов, по умолчанию `INFO` |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | Параметры базы данных |

`DJANGO_SETTINGS_MODULE`, `POSTGRES_HOST` и `POSTGRES_PORT` compose задаёт сам.

Остановка:

```bash
make docker-down
```

## Проверки и тесты

Единая статическая проверка:

```bash
make check
```

Она запускает Django system check, Ruff lint, Ruff format check и mypy.

```bash
make test
```

Покрыты serializers, формат ошибок, calculator, сервис создания заказа,

промокода. Конкурентные тесты требуют PostgreSQL.

## Принятые ограничения

- пользователь передаётся через `user_id`, поскольку так задан API-контракт;
- endpoint не требует аутентификации;
- один промокод может разрешать одну категорию либо все категории;
- успешно созданный заказ навсегда занимает использование промокода;
- отмена заказа, доставка, налоги и идемпотентность HTTP-запросов не входят в
  текущий scope.
